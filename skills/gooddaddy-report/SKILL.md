# 굿대디 리포트 — 주말 육아 나들이 계획서

아빠가 "이번 주말 애 데리고 나갈게"라고 말하는 건 쉽다. 아내가 안심하는 건 **어디를, 몇 시에, 낮잠과 밥은 어떻게** 가 한눈에 보일 때다. 이 스킬은 그 질문에 먼저 답하는 카드 5장 안팎의 계획서를 만든다.

결과물이 통과해야 할 기준은 하나: **아내가 첫 장을 열고 10초 안에 "오 괜찮네, 다녀와"라고 할 수 있는가.** 그래서 결론·날씨·한마디는 첫 장에, 자세한 건 뒷장에 둔다. 아이 컨디션(낮잠·밥·귀가)에 대한 배려가 눈에 띄게, 확인 안 된 정보는 확인 안 됐다고.

## 전체 흐름

1. 프로필 불러오기 (없으면 짧은 인터뷰 후 저장)
2. 날짜 확정 + 날씨 조사
3. 후보 10~15곳 수집 → 이동시간 계산 → 5곳 선정
4. 장소마다 식당 1~3곳
5. 1순위 하루 시간표 + 나머지 출발 힌트
6. plan.json 작성 → 카드 이미지(보통 5장) 렌더 → 눈으로 검수
7. 전달: 이미지 순서대로 + 아내에게 보낼 한 줄 메시지

판단 기준은 두 참고 문서에 있다. 필요한 시점에 읽는다:
- `references/place-selection.md` — 3~4단계 (후보 검색법, 점수표, 5곳 조합 규칙, 식당 거르는 순서)
- `references/parenting-rules.md` — 2·5단계 (월령별 기본값, 낮잠-이동 맞추기, 오픈런, 식사, 날씨 판단, 귀가)
- `references/plan-schema.md` — 6단계 (JSON 필드와 빌드 명령)

## 1. 프로필

위치: `~/.gooddaddy-report/profile.json` (Windows는 `%USERPROFILE%\.gooddaddy-report\profile.json`)

있으면 읽고 한 줄로 요약해 보여준 뒤 바로 진행한다 ("하준 18개월 · 상암동 출발 · 차 · 낮잠 13~15시 기준으로 짤게"). 요청 문장에 달라진 정보가 있으면("이번엔 둘째도 같이") 그걸 우선하고, 계속 쓸 정보인지 물어 저장한다.

없으면 **한 메시지로** 묻는다. 여러 번 왔다 갔다 하면 귀찮아서 그만둔다. 사용자가 요청에 이미 말한 건 다시 묻지 않는다.

```
주말 계획 짜기 전에 딱 한 번만 여쭤볼게요 (다음부턴 저장해둔 걸로 바로 짭니다)
1. 출발 동네 (예: 마포구 상암동)
2. 아이 애칭과 생년월 (예: 하준, 2025년 3월) — 둘 이상이면 모두
3. 평소 낮잠 시간 (예: 오후 1시~3시)
4. 이동 수단: 자가용 / 대중교통
5. 누구랑 가나요: 아빠+아이 / 온 가족
6. 리포트 받는 분 호칭 (예: 여보, ○○엄마)
7. (선택) 편도 최대 몇 분까지 괜찮은지, 좋아하는 것·피할 것, 알레르기
```

저장 형식:

```json
{
  "home": "서울 마포구 상암동",
  "homeCoord": "37.5716,126.8728",
  "children": [{ "name": "하준", "birth": "2025-03", "naps": ["13:00-15:00"], "notes": "계란 알레르기" }],
  "transport": "car",
  "party": "아빠+아이",
  "recipient": "여보",
  "author": "하준 아빠",
  "maxDriveMin": 60,
  "likes": ["동물", "물놀이"],
  "avoid": ["사람 많은 곳"],
  "visited": [{ "name": "서울대공원", "date": "2026-09-19" }]
}
```

`homeCoord`는 첫 route.mjs 실행 결과에서 채운다. 월령은 **오늘 날짜 기준으로 매번 다시 계산**한다 (저장된 월령은 금방 틀려진다). 프로필은 이 컴퓨터에만 저장되고, 리포트에는 동 단위까지만 쓴다.

파일 시스템을 쓸 수 없는 환경이면 인터뷰 결과를 대화에서 그대로 쓰고, 끝에 "다음에 이 블록을 붙여 넣으면 바로 짜드려요"라며 JSON을 보여준다.

## 2. 날짜와 날씨

- 오늘 날짜로 "이번 주말"을 계산한다. 이미 토요일 오후 이후면 일요일, 일요일 오후면 다음 주말로 보고 한 줄로 알린다.
- 토·일이 정해지지 않았으면 두 날의 예보를 비교해 나은 날로 짜고 이유를 적는다. 공휴일·연휴가 붙으면 혼잡도를 올려 판단한다.
- 기상청 단기·중기 예보(또는 포털 날씨)를 검색해 **최저·최고기온, 강수확률(오전/오후), 미세먼지, 자외선, 바람**을 모은다. 5일 이상 남았으면 예보 정확도가 낮다고 적고, 플랜 B를 더 튼튼하게 둔다.
- 날씨 → 실내/야외 비중 판단은 `parenting-rules.md` 5절.

## 3. 장소 5곳

`place-selection.md`를 읽고 따른다. 핵심만:
- 여러 결의 검색으로 10~15곳을 모은다 (정석·월령·이번 주 행사·날씨 대응·공공시설).
- 이번 주말 운영 여부·예약·오픈런·편의시설을 확인한다.
- 이동시간은 스크립트로 한 번에 계산한다:
  ```bash
  node <이 스킬 경로>/scripts/route.mjs --from "<home 또는 homeCoord>" --region "<시·도>" --to "<후보1>" --to "<후보2>" --depart <예정 출발 ISO 시각> [--mode transit]
  ```
  `--region`을 꼭 넣고, ⚠ 오매칭 의심이 뜨거나 매칭 이름이 엉뚱하면 검색한 좌표로 다시 돌린다. 차가 없는 가족은 `--mode transit`으로 돌린 뒤 상위 후보의 실제 노선·엘리베이터 출구를 검색으로 확인한다 (`place-selection.md` 2절). `KAKAO_REST_API_KEY` 환경변수가 있으면 교통 예측을 반영한 카카오 길찾기를 쓰고, 없으면 OSRM 도로거리에 주말 보정을 곱한 추정치다.
- 점수표로 순위를 매기되, 5곳 조합 규칙(실내 1곳 이상, 가까운 곳 1곳 이상, 종류 중복 피하기, 다녀온 곳 제외)을 지킨다.

## 4. 식당

장소마다 1~3곳 — 1순위는 2~3곳, 나머지는 1~2곳. **식당 칸이 빈 장소는 만들지 않는다.** 조건에 맞는 곳이 안 보이면 반경 넓히기 → 시설 안 푸드코트·옆 백화점/마트 → 검색어 바꾸기 → 체인점(확인 필요) → 도시락·집에서 먹고 출발 같은 대안 순으로 넓혀서 채운다. 노키즈존 여부를 가장 먼저 거르고, `menu`에 **아이는 뭘 먹으면 되는지**까지 쓴다. 기준은 `place-selection.md` 4절.

## 5. 시간표

1순위 장소 하나로 **집 출발 전 준비부터 귀가까지** 짠다. `parenting-rules.md` 2·3·4·6·7절 순서대로:
아이 고정 시간(낮잠·식사) 먼저 → 운영시간·오픈런 → 이동을 낮잠에 맞춰 출발·귀가 결정 → 11:30 전 점심 → 간식·기저귀 포인트 → 버퍼.

시간표는 **7~10줄**로 짧게 — 카드 한 장에 들어가야 한다. 기저귀·간식 같은 작은 일은 앞뒤 줄의 detail에 합친다.

특수 상황은 시간표 `detail`이나 `itineraryNote`에 **왜 이 시각인지** 드러나게 쓴다. 이게 이 리포트의 가치다:
- "편도 70분 → 낮잠 시작 12:50에 맞춰 12:40 출발, 차에서 재움"
- "선착순 입장이라 개장 30분 전 도착 → 8:50 출발"
- "15시부터 귀경 정체 → 14시 귀가 출발, 오후 낮잠은 차에서"

2~5순위는 `departHint`에 출발 시각과 이유 한 줄만.

## 6. 리포트 만들기

작업 폴더는 현재 작업 디렉터리 아래 `gooddaddy-report-YYYYMMDD/` (날짜는 나들이 날). **`references/plan-schema.md`를 읽고** (슬라이드 구성과 필드별 글자 수 예산이 있다) `plan.json`을 쓴 다음:

```bash
node <이 스킬 경로>/scripts/build.mjs gooddaddy-report-20260919/plan.json
node <이 스킬 경로>/scripts/render.mjs gooddaddy-report-20260919/report.html
```

글쓰기 톤 — 받는 사람은 아내다:
- `headline`은 결론 한 문장: 장소 + 아이 컨디션 배려 한 가지. ("토요일은 서울대공원, 낮잠은 가는 차에서 재울게")
- 반말·다정한 보고체. 과한 애교나 "제가 알아서 다 할게요!!" 같은 과장은 오히려 신뢰를 깎는다.
- 아내가 속으로 물을 질문에 먼저 답한다: 낮잠은? 밥은? 몇 시에 와? 비 오면? 애 뭐 챙겨?
- `message`: 아내에게 한마디. 아빠+아이만 나가는 계획이면 아내가 쉬는 시간을 짚어 준다 ("오전은 푹 자"). 온 가족이면 아내가 신경 쓸 게 없다는 점을.
- 확인 못 한 정보는 `caution`이나 `notes`에 "확인 필요"로. 지어내지 않는다.

결과는 `report-01.png`, `report-02.png` … 각 1080×1350, 오른쪽 위에 `1 / N` 번호가 붙은 카드 이미지다. 내용이 넘치면 스크립트가 알아서 다음 장으로 넘기지만, **목표는 5장(많아도 6장)** 이다:
- 7장 이상 → 글자 수 예산을 넘긴 필드를 줄이고 다시 빌드·렌더.
- 종료 코드 5(⚠ 넘친 장) → 그 장의 긴 글을 줄인다.
- 이미지를 **직접 열어 본다.** 한두 줄만 넘어간 거의 빈 장, 잘린 글자, 빈 섹션이 있으면 고친다.
- 종료 코드 3(브라우저 없음) → HTML만 전달하고, 브라우저로 열면 슬라이드가 세로로 쌓여 보인다고 안내한다.

## 7. 전달

사용자에게 보여줄 것:
1. 카드 이미지를 **번호 순서대로** (파일 전달 도구가 있으면 그걸로) + HTML. "카톡에 1번부터 순서대로 올리면 된다"고 한 줄 안내.
2. 카톡에 이미지와 같이 보낼 1~2줄 메시지 초안.
3. 채팅에는 짧은 요약만: 1순위와 출발 시각, 사용자가 **직접 해야 할 일**(예약 오픈 시각, 전날 확인할 것).

메일·메신저 도구가 연결돼 있어도 **자동으로 보내지 않는다.** 보내 달라고 하면 받는 사람과 내용을 보여주고 확인받은 뒤 보낸다.

마지막으로 프로필 `visited`에 1순위를 추가할지 묻는다 (다녀온 뒤에). 다음 주 추천이 겹치지 않게 된다.
